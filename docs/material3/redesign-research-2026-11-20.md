# MPEI Lite redesign research and proposal

**2026-11-20 · Baseline `059a9ac` · Approved design and verification**

The handoff establishes the four destinations, the continuous timetable, one Expressive motion system, and Settings in the Schedule overflow. It leaves the layout details, scroll implementation, and motion treatments open. The proposal below covers those choices and records the evidence needed before changing the app.

## Timetable options

| Technique | Trade-off |
| --- | --- |
| **Day-keyed `LazyRow` with start snapping** | Native drag and fling with one lazy sequence. Monday can include a physical seam and any future width adjustment without rewriting snap targets. Derive the week header from the visible day nearest the leading snap position. |
| **Day-sized `HorizontalPager`** | Native drag, built-in snapping and a ready-made current page. All pages share a width, so a Monday seam must fit inside the page. It can cap fling distance. Validate how adjacent visible pages and scroll offsets behave when the viewport changes. |
| **Week-level pager or linked horizontal scrollers** | A week-level snap cannot provide the same stable day stop at each side of a boundary. Linking a day scroller to a separate week scroller would add gesture and state synchronization that the two single-scroller options avoid. |

[Compose snapping APIs](https://developer.android.com/reference/kotlin/androidx/compose/foundation/gestures/snapping/package-summary), [Pager in Compose](https://developer.android.com/develop/ui/compose/layouts/pager), [Nested scrolling modifiers](https://developer.android.com/develop/ui/compose/touch-input/scroll/nested-scroll-modifiers)

## Prototype evidence

The disposable Android prototype uses the existing theme, fake lesson data and the pinned Compose build. Its toggles compare both scroll implementations and the card treatments. Both variants stay in one horizontal sequence. The APK uses a separate application ID and contains no account or network integration.

| Check | Observation on the API 37 emulator |
| --- | --- |
| Slow horizontal drag and day snap | Both moved while the pointer was down. The lazy row advanced through Fri 20, Sat 21, Sun 22 and Mon 23, then settled on Mon 23. Reversing the drag visited Sun 22 and Sat 21 and settled back on Fri 20. The date header changed as the leading day changed. |
| Day pager comparison | The pager followed the same days on the outward drag, reached Mon 23 while moving, and then settled back to Sun 22. The reverse gesture passed through Thu 19 and settled on Fri 20. This behavior is specific to the tested pager snap configuration. |
| Explicit week control and details | The next-week action jumped to Mon 23. Opening a lesson showed the Material sheet. Its teacher action closed the sheet and opened a sample teacher route over the group grid. A left-edge Back preview kept the teacher content visible, revealed the group timetable, and committed back to Mon 23. |
| Cards and density | At 411 dp and standard font size, three day columns fit. A room line fit short sample labels and used taller rows. Some names already wrap in real usage, so reserve that space for abbreviations. The three tonal roles and one/two/three marks made type discernible in the screenshot, but the cue still needs a discoverability check. |
| Frame sample | One earlier debug-prototype run of six alternating swipes returned 167 frames, p50 34 ms, p95 77 ms and 68 missed deadlines in `dumpsys gfxinfo`. The emulator was running at 60 Hz and also showed launcher failures. This sample documents jitter on that environment. A matched physical-device run is needed to judge the product's frame pacing. |

**Recommendation** — use the snapping day-keyed lazy row. It tracked the test gesture and settled at the visible week boundary without introducing another gesture owner or any library. Use a thin Monday seam, tonal day header, room in the sheet, and a font-aware time gutter and column count.

## Proposed design

- Use one horizontally lazy sequence of calendar days with a common period gutter and a vertically scrollable grid. Mondays get a narrow separator and a distinct header treatment. Keep Sunday in the sequence so either direction across the seam is adjacent. Show the week of the leading snap day, with previous, next and a date jump in the Schedule app bar. Keep every explicit jump distinct from ordinary swiping.
- Put an abbreviation and a small non-color marker for type inside the card. Use matching theme color roles and a full semantic label. Keep room in the details sheet to leave enough space for long Cyrillic abbreviations and larger fonts. Generate abbreviations on the official name, with an editable local override and reset. Persist overrides in the existing DataStore. Use a case-insensitive normalized subject key and keep the official title intact.
- Use fixed rows for the published periods and keep overlapping lessons separately tappable. Retain access to genuine off-slot start times; check data samples before selecting the smallest row treatment that fits them. Fetch visible weeks plus the immediate neighbors through the existing repository with request deduplication. Store the visible calendar date and scroll offset so restoring around a week rollover keeps the same day. Use Moscow dates consistently for both display and requests. The current grid clock uses Moscow while the ViewModel derives the request week from the device's default date.
- Use one Material modal sheet for lesson name, time, type, room, teacher, groups, and abbreviation editing. Dismiss it before navigating to a teacher timetable anchored to the lesson date. Keep the group route and both scroll axes beneath it. Use a disambiguation list if the lecturer name maps to multiple results. Report a missing result while leaving the original schedule usable.
- Keep the existing shell and data owners. Add destination-scoped saveable state and explicit reset actions for each destination. Separate active destination from nested route state so tab switches restore prior routes and Back from a non-Schedule root returns straight to Schedule. Existing view models own drafts, notifications, login and async updates. Compare this focused change with Jetpack Navigation's saved-state back stacks only if the shell cannot preserve and test the current UI owners cleanly. [Multiple back stacks](https://developer.android.com/guide/navigation/backstack/multi-back-stacks)
- Start with a short effects transition for peer tabs and the shared spatial surface for nested screens, including teacher timetable. Handle Back from either edge and cancel back to full size. Use an ordinary exit for toolbar and three-button Back. A lesson sheet already supplies its entry/exit motion. Add a shared element only if both endpoints reliably exist during real scrolling and a prototype demonstrates clearer hierarchy. [Shared elements and navigation](https://developer.android.com/develop/ui/compose/animation/shared-elements/navigation)
- Keep Material search and its IME and focus behavior. Put Settings in Schedule's collapsed app-bar overflow. Keep updates and log copy inside the existing Settings screen.

Implement in three reviewable increments. Start with destination retention, reselect, Back and peer/detail motion, with existing regression coverage as the baseline. Then integrate the continuous grid, week loading and jumps, lesson details, abbreviations and teacher navigation. Relocate Settings with the Schedule app bar and test the complete shell on emulator and device. Keep BARS, Mail and Map layouts in place throughout.

## Verification criteria for implementation

1. Add data tests for abbreviations, overrides, overlaps, unknown lesson times, week mapping and request lifetime. Cover week jumps, week rollover, both directions over the Sunday/Monday boundary, and restoration after a window configuration change.
2. Exercise each tab's root and deepest representative route with tab switching, reselect and Back. Verify Mail detail search and compose navigation, draft preservation, BARS refresh and planner, Map camera, Settings actions, and Back from Schedule to Android.
3. Verify phones and expanded windows in light/dark, increased fonts, keyboard, gesture and three-button navigation, and TalkBack. Capture both-edge Back progress and cancellation with actual touch input.
4. Measure baseline and changed builds on the same physical device with OS version, refresh rate, build mode and repeated interactions recorded. Use the existing frame profiler to identify input, layout, draw and GPU costs. Collect an Android Studio or Perfetto system trace with frame deadlines and inspect recomposition, layout and render work when overruns cluster around a flow. Report sample counts, p50/p95 frame duration, deadline overruns and any callback drops. Emulator traces can expose functional problems; use physical-device data for performance conclusions. [Composition tracing](https://developer.android.com/develop/ui/compose/tooling/tracing), [Macrobenchmark](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview), [Android rendering guidance](https://developer.android.com/topic/performance/issues/render)

Registry statuses remain under implementation review. Account-backed behavior, TalkBack, and performance on a representative physical device require verification.

## Implementation and validation

The app now uses the date-keyed snapping timetable. Date headers stay pinned as the time gutter and lesson rows scroll vertically together. Multiple lessons at one start time retain distinct touch targets. Unknown and off-slot times stay accessible. A user can edit or reset a lesson's local abbreviation in the sheet. The teacher timetable uses the existing lecturer search and week cache while keeping the selected group and widget target. Dates are indexed over 2000–2100 and weeks use the Moscow date. Week loading and error states overlay the grid so a boundary drag does not move the rows vertically.

The four destinations save their Compose state separately. Each owns its nested back actions and reselect behavior. The persistent bar and rail stay outside the peer transition. A cancellable effects transition now includes the destination app bar, so the Schedule preview has its final insets during root Back. The detail overlay keeps the parent mounted and hides covered controls from accessibility where the new timetable, Mail and portal stack layers overlap. Mail portal history and page position live in the Mail ViewModel for tab changes and activity recreation. Browser history has the lifetime of the app process.

The Windows Gradle wrapper built the debug and instrumentation APKs and passed lint and 317 JVM tests. Both Python policy checks and all 20 Python tests passed. The API 37 baseline reproduced three failures in nine tests, involving an old Mail portal navigation assertion, ambiguous Schedule search-input selection, and a second exit animation after Mail predictive Back. All 13 affected tests in the first implementation run passed. The independent source review prompted further fixes and tests for resumed lesson sheets, large-font pinned dates, the root Back preview position, and a BARS route whose discipline disappears while the destination is unmounted. The final set of 22 targeted tests passed across two runs. The first run passed 21 tests. The remaining Map keyboard test had a stale entry selector from the previous navigation shell. A rerun with the current selector passed the original building-selection assertions. An emulator Back key at Schedule root finished MainActivity and returned to the preceding task.

### Frame capture

An Android API 37 emulator system trace recorded the debug app during the timetable and Mail overlay fixture tests. The app activity's FrameTimeline surface produced 66 positive-duration samples with a 64.07 ms median and 435.65 ms 95th percentile. FrameTimeline classified 64 samples as app deadline misses and one as a dropped frame. This sample includes fixture startup and test automation. The emulator hit a separate bind-application ANR while collecting another trace and logged an input-focus ANR during a cold launch that eventually drew after about 40 seconds. These runs leave startup and smoothness acceptance open. The fixture trace was queried with Perfetto Trace Processor. The Android Studio profiler view could not be verified from the available desktop session. [Android Studio profiling](https://developer.android.com/studio/profile), [FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline)

The trace includes system rendering and scheduling events. The fixture capture does not establish per-composable recomposition, phase costs or allocations. A matched before/after run on physical hardware still needs to cover timetable drag, modal sheet, peer switch, BARS refresh and Mail compose, with frame deadlines and Compose tracing. Confirm real OWA history and authenticated Mail and BARS flows, TalkBack traversal, gesture behavior from both edges, and full light/dark and expanded-window rendering on device before closing the affected Material 3 audit entries.
